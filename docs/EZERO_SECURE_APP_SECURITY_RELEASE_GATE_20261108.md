# E-ZERO Secure App — 2026-11-08 security-first release gate

**Status:** STAGING threat model and CI protection. NOT a security certification or a claim that the app cannot be hacked.

## Non-negotiable product decisions
1. Keep the verified audio/video WebRTC engine working. Pin the seven successful stage modules in `tests/ezero_verified_success_lock_20261108.json` by exact Git object hash. A change to a pinned file fails CI until explicitly reviewed and revalidated.
2. Preserve the current public build. Only a separate Render staging service/branch may get unverified features; no credentials or production merge via this review.
3. Camera/microphone only on user action and browser permission. No background polling, recording, screenshot blocking claims or hidden media access.
4. A QR URL or name/DP is **not** human identity proof. Caller and callee each verify signed ephemeral identity. Replays, expired invitations, mismatched peer fingerprints or unsupported signatures fail closed.
5. WebRTC calls use DTLS-SRTP and encrypted SCTP data channels; separate the concept of *transport encryption* from app-controlled *end-to-end encryption* and audited key lifecycle.
6. Do not store or transmit TURN long-term secret/API token in the browser. Rotate short-lived TURN credentials generated by backend service, with quotas and revoked keys.
7. Remove recordings, voice notes and ephemeral messages by their declared timers in the app; avoid any claim that screenshots or the recipient's external recording can be prevented.
8. Origin-specific WSS handshakes must be approved on the **server**, with authenticated room access, per-message permissions, bounded payload and connection rates, expiry and abuse controls. Browser CSP alone is not server authorization.

## Threats and required tests before public rollout
| Threat | Protection | Current evidence / next verification |
|---|---|---|
| Malicious QR, other site, token replay | Exact origin/path + signed identity, random per-room secret, short TTL, one-time join | Existing code guard, add negative real two-phone/replay tests |
| Fake friend or impersonated photo | Cryptographic peer fingerprint linked to signed SDP; user naming distinct | Client stage checks exist, third-party identity still unproven |
| WebSocket hijack / flood | Server strict Origin allowlist, per-message auth, max 32–64 KiB, rate and room caps, idle expiry | **Server worker inspection still required** |
| Browser injection / cross-site scripts | CSP self-hosted scripts, no unsafe-eval / unsafe-inline, HTML-safe DOM APIs | New automated CI baseline |
| Microphone/camera privacy | Explicit consent, only in-user-action capture, hangup releases tracks | Existing browser camera/voice CI, physical phones pending |
| Leaked TURN credentials | Server-only TURN API key, short-term browser credentials, quota monitoring | Not deployed; separate trial |
| Missed calls / poor NAT route | Cloudflare Realtime TURN conditional fallback, avoid silent reconnect | Evaluate only after keys, billing and acceptance tests |
| Changed successful module | Pin expected Git blob SHA-1, CI fail until reviewed | New verified-success gate, not a replacement for security review |
| Vulnerable dependencies | CodeQL JS + Python and dependency review | Add new workflow; check scan eligibility and findings |
| Voice note / speaker quality | MediaRecorder supported mime, bounded bytes, actual both-phone audible tests | Existing synthetic browser test only |

## Release protocol
- A: Baseline and static tests PASS.
- B: Adversarial isolated tests PASS: wrong-origin QR, expired room, replay, forged signature, server flood/rate and timeout.
- C: Two real Android/iOS phones test QR, both audio directions, video, speaker, voice notes, camera permission, hangup, multiple networks.
- D: Privacy/legal policy and independent security audit reviewed.
- E: Release staging candidate only after approval, freeze a new digest manifest and keep rollback artifact.
- No production publish when any security-critical gate is FAIL/UNKNOWN.

## Render HTTPS security-header deployment gate (NOT yet applied)
Render Static Sites supports response headers via **Settings → Headers** or a reviewed Blueprint. HTML meta CSP does **not** enforce the `frame-ancestors` rule. Configure headers on the isolated **test** host before public release; verify they are actually present in HTTP responses and perform two-phone audio/video/QR regressions afterward. Never disable camera/microphone permission globally.

Required candidate rules for `/*`:
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- `Permissions-Policy: camera=(self), microphone=(self), geolocation=(), payment=(), usb=()`
- `Content-Security-Policy: frame-ancestors 'none'; default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; media-src 'self' blob:; connect-src 'self' wss://ezero-browser-signaling-render-test.coma39658.workers.dev; manifest-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'`
- `Strict-Transport-Security: max-age=31536000` on a host serving exclusively HTTPS (do not add `includeSubDomains` without reviewing all subdomains).

The test host's existing CSP must be examined for any extra safe necessary directives before applying it. These headers are **recommended**, not yet verified as configured. Refer to https://render.com/docs/static-site-headers.
